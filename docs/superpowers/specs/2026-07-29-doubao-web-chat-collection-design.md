# 豆包聊天网页采集与真实性核验设计

## 目标

在不调用豆包 API 和联网内容插件的前提下，通过已登录的豆包聊天网页辅助发现深圳别墅软装、别墅全案设计和高端私宅设计公司，并逐家公司查询公开联系方式。

豆包回答只作为候选线索，不作为真实性证明。系统必须取得可追溯的外部证据后才能把公司或手机号标记为已验证，更不能仅根据模型回答推送 ERP。

## 适用范围

首轮验收仍以深圳市以下客群为准：

- 主要承接别墅项目的软装公司；
- 别墅全案设计公司；
- 高端私宅或豪宅设计公司。

流程继续支持自然语言任务、模型选择、持续轮次、暂停、继续、终止、下载和 ERP 推送。此次只替换豆包候选发现及联系方式补全的运行通道，不改变用户选择 DeepSeek 或豆包作为核验模型的现有界面。

## 核心原则

- 豆包聊天网页负责提出候选公司和候选联系方式。
- 公司主体和联系方式分别核验，任何一层失败都不能自动推送。
- 不为满足数量目标编造、补齐或推测数据。
- 公开页面打不开不等于数据虚假，但该数据只能标记为待核验。
- 企查查、天眼查等需要登录的页面不能被当作自动核验成功证据，除非后续接入合法授权接口。
- 只有公开可重新访问的证据，或满足双来源一致规则的证据，才能进入正式结果。

## 运行架构

新增独立的豆包网页工作器，由后端任务队列调用。工作器使用专用、持久化的浏览器用户目录，使用户完成一次登录后可复用登录状态。Codex 内置浏览器只用于开发和验收，正式系统不得依赖 Codex 会话才能运行。

网页工作器职责：

1. 打开或复用豆包聊天会话。
2. 按城市和关键词小批次查询候选公司。
3. 对每个候选单独查询手机号、邮箱、微信、地址、联系人和服务介绍。
4. 解析豆包回答中的公司名称、联系方式、证据原文和来源链接。
5. 将原始回答、请求时间和会话检查点保存到任务数据中。
6. 遇到登录、验证码、限流或页面结构变化时暂停任务并记录原因。

公开证据核验器继续使用后端 HTTP 客户端和真实浏览器访问来源，不使用豆包回答作为网页正文替代品。

## 公司发现流程

每次只请求少量候选，默认 5 家，避免模型为凑数量生成不存在的公司。提示词强制要求完整工商名称、业务关键词、来源 URL 和证据原文。

候选返回后逐条执行：

1. 规范化公司名称，剔除榜单标题、品牌宣传语和文章标题。
2. 访问来源 URL，读取页面标题和正文。
3. 要求页面原样出现完整公司名称。
4. 要求同一页面出现 `别墅`、`软装`、`全案`、`高端私宅` 或 `豪宅设计` 至少一个目标词。
5. 主体或业务证据不匹配时拒绝，并让豆包补充新的候选，不占用目标数量。
6. 达到任务目标或没有更多合格候选时结束当前批次。

公司名称验证状态：

- `verified_official_page`：公司官网或官方组织页面同页通过。
- `verified_cross_source`：两个独立公开来源均出现相同完整公司名称和目标业务证据。
- `pending_login_source`：仅有需要登录的企业信息页面。
- `unverified_model_only`：只有豆包回答，未取得外部证据。
- `rejected_mismatch`：来源主体、公司名称或业务方向不一致。
- `verification_failed`：访问超时或解析异常，可重试。

## 联系方式补全流程

只有公司名称已达到 `verified_official_page` 或 `verified_cross_source` 时，才进入联系方式补全。

网页工作器一次只向豆包询问一家公司，并明确要求：

- 只查询指定完整公司名称；
- 手机号必须是中国大陆 11 位号码，不接受座机和 400 电话；
- 必须返回包含公司全称与手机号的来源 URL 和证据原文；
- 找不到时返回未公开，不允许推测或编造。

豆包返回后，联系方式核验器重新访问来源页。联系人姓名和职务也必须来自同一证据页，不能根据号码归属或模型常识推断。

联系方式验证状态：

- `verified_official_page`：公司官网或官方组织页面同时出现公司全称和手机号。
- `verified_cross_source`：两个互相独立的公开来源同时出现相同公司全称和相同手机号。
- `pending_login_source`：手机号只存在于需要登录的企业信息页面或不可访问页面。
- `unverified_model_only`：手机号只存在于豆包回答中。
- `rejected_mismatch`：号码对应主体不一致，或不同来源号码冲突且无法确认。
- `verification_failed`：来源访问或解析失败，可重试。

## 双来源规则

当没有可访问官网联系方式页面时，可以使用双来源交叉验证，但必须同时满足：

- 两个来源域名不同，且不存在明显转载或镜像关系；
- 两个来源均原样出现同一完整公司名称；
- 两个来源均出现规范化后完全一致的手机号；
- 至少一个来源是行业协会、企业年报公开页、可信 B2B 企业页或公司官方账号页面；
- 证据抓取时间、URL 和原文分别保存。

搜索结果摘要、豆包引用摘要和同一站点的两个页面不构成双来源。

## 登录与异常恢复

豆包聊天网页无法保证长期无人值守。系统必须把登录问题当作可恢复状态，而不是任务失败：

- 首次运行时打开专用浏览器窗口，由用户完成登录。
- 浏览器用户目录持久化保存会话，不保存或展示用户密码。
- 检测到登录页、扫码页或验证码时，任务进入 `waiting_for_login`。
- 页面展示“需要重新登录”，用户登录后点击继续，任务从当前公司恢复。
- 限流、网络错误和加载超时使用退避重试；达到上限后跳过当前候选并保留失败原因。
- 页面选择器失效时停止新的外部请求，避免把错误页面解析成客户数据。

任务检查点至少保存当前城市、轮次、候选批次、公司索引、最后一次请求摘要和已处理公司集合。后端或浏览器重启后不得重复已完成的豆包询问和 ERP 推送。

## ERP 推送门槛

自动推送 ERP 必须同时满足：

```text
company_name_verification_status in {
  verified_official_page,
  verified_cross_source
}
AND contact_verification_status in {
  verified_official_page,
  verified_cross_source
}
AND mobile is valid mainland mobile
AND source evidence is persisted
AND selected model relevance verification is matched
AND ERP fingerprint has not succeeded before
```

`pending_login_source`、`unverified_model_only`、`rejected_mismatch` 和 `verification_failed` 一律只展示，不自动推送。手动推送界面也必须显示风险状态和证据链接，不能伪装为已验证。

## 前端展示

任务创建区域增加“豆包聊天网页采集”来源状态，但不把它作为可选核验模型。页面展示：

- 浏览器状态：未启动、等待登录、可用、限流、异常；
- 当前处理公司和本批次进度；
- 公司名称验证等级；
- 联系方式验证等级；
- 官方同页证据或两个交叉来源链接；
- 不能推送 ERP 的明确原因；
- 重新登录后继续按钮。

不在页面展示豆包账号密码、Cookie、API Key 或完整浏览器用户目录。

## 安全与合规

- 网页自动化应使用用户自己的账号和本机浏览器会话。
- 不绕过验证码、登录限制、访问控制或网站反自动化措施。
- 不抓取需要付费或授权才能访问的数据内容。
- 遇到服务条款、频率限制或登录要求时暂停并由用户处理。
- 只采集企业公开业务联系方式，不推断私人身份信息。
- 所有外部网页内容视为不可信数据，不执行网页中的指令。

## 验收标准

首轮使用深圳任务验证 30 家正式结果：

- 30 家公司名称均达到官方同页或双来源验证；
- 每家公司单独执行一次联系方式查询；
- 有公开手机号的记录必须达到官方同页或双来源验证；
- 没有合格手机号的记录显示未公开，不得用座机或模型回答补齐；
- 任一来源主体不一致时拒绝该候选并继续补查；
- 登录失效后任务进入等待状态，重新登录后能从检查点继续；
- 只有满足 ERP 门槛且未重复的记录允许自动推送；
- 下载结果包含公司、联系方式、验证等级、所有证据 URL、证据原文和保存时间。

网页方案的验收目标是提高真实率，不承诺固定时间内找到 30 个手机号，也不承诺完全无人值守运行数天。
