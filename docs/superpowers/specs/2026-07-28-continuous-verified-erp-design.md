# 持续采集、真实性验证与 ERP 安全推送设计

## 目标

为公司正式采集任务增加可长期运行的持续模式。任务在同一个任务记录中按轮次循环发现、补全和验证企业线索，每轮最多发现 100 家候选，轮次结束后冷却 10 分钟再继续，直到用户主动暂停或终止。

系统必须先展示并保存采集结果，再决定是否推送。只有同时满足以下条件的线索才允许自动推送 ERP：

- 存在有效的中国大陆手机号码；
- 存在可追溯的公开来源链接；
- 真实性验证结果为 `single_model_match` 或 `model_consensus_match`；
- 尚未以相同联系方式或 ERP GUID 成功推送。

模型拒绝、模型分歧、验证失败、缺少手机号或缺少来源链接的线索只保留在采集结果中，绝不自动推送。系统不得为了凑数量编造公司、联系方式或来源。

## 首个正式任务范围

首个正式任务只采集深圳市以下客群：

- 专做别墅项目的软装公司；
- 别墅全案设计公司；
- 高端私宅或豪宅设计公司。

持续模式本身保持通用，后续可由其他自然语言需求创建，但本次验收以深圳任务为准。

## 用户操作

任务创建区域在现有模型选择区下方新增两个独立开关：

- `持续采集`：默认关闭。开启后，同一任务自动进入下一轮，不创建重复任务。
- `验证通过后自动推送 ERP`：默认关闭。开启前必须确认 ERP 已配置，并且至少选择一个可用验证模型。

自然语言输入仍只描述客群和范围，模型选择继续使用当前输入框下方的选择区域、模型顺序和配置状态，不改变现有交互方式。模型由用户在现有界面中勾选，系统不得根据自然语言替换或追加任务的核验模型：

- 用户选择一个已配置模型时，使用该模型完成候选发现和单模型核验；
- 用户选择多个已配置模型时，使用所选模型发现候选并进行交叉核验；
- 未配置的模型继续显示在原位置并置灰，不允许勾选；
- 任务一旦创建，后端严格使用该任务保存的模型列表，不因轮次切换或重启而改变。

联系方式补全保持上一版本方案，不受核验模型选择影响：候选公司最后仍然逐家公司调用已配置的豆包联网能力查询手机号、邮箱、微信、地址、服务介绍和公开来源。不得改为 DeepSeek 或其他核验模型补全，也不得在豆包失败时自动回退到其他模型。

用户点击开始后，可以离开页面；后端任务继续运行。

普通一次性任务保持原行为。持续模式和验证后推送均不得因升级自动开启，旧任务缺少新字段时统一按关闭处理。

## 单轮执行流程

每一轮按以下顺序执行：

1. 根据自然语言目标生成并轮换深圳相关关键词，包括别墅软装、别墅全案设计、高端私宅设计和豪宅设计等组合。
2. 使用已配置模型和底层公开网页检索发现候选，本轮最多接收 100 家。
3. 将候选与本任务全部历史线索按规范化公司名、手机号、邮箱、微信号和来源链接去重。
4. 只对本轮新增候选逐家公司补全联系方式、地址、服务介绍和公开来源。
5. 先保存并展示补全结果，再使用所选模型进行真实性与相关性验证。
6. 对满足安全门槛的新增线索逐条推送 ERP；单条成功或失败都立即持久化。
7. 保存本轮统计和检查点，进入 10 分钟冷却。
8. 冷却结束后开始下一轮。即使本轮新增为零，也继续下一轮并轮换关键词。

每轮“最多 100 家”指候选发现上限，不保证得到 100 条可推送线索。真实性和联系方式优先于数量。

## 去重与 ERP 幂等

历史去重贯穿整个持续任务，而不是只在单轮内生效：

- 有手机号时优先使用规范化手机号作为唯一识别码；
- 无手机号时依次使用规范化邮箱、微信号和公司名加城市；
- 同一公司出现新的公开来源时可以补充来源证据，但不新增重复线索；
- ERP 继续使用稳定的 `customerAccountGuid` 和成功指纹作为最终幂等保护；
- 已经 `succeeded` 的 GUID 在任务继续、页面刷新或后端重启后均不得再次发送。

ERP 逐条串行推送，成功标准保持为响应中的 `errCode == 0`。单条失败记录错误并继续后续线索，不阻塞本轮；失败线索可以通过现有重试机制重试，但不得绕过验证门槛。

## 任务状态与持久化

任务保留现有 `queued`、`running`、`pausing`、`paused`、`terminating`、`terminated` 等生命周期状态，并新增持久化的持续执行信息：

- `continuous_mode`：是否持续循环，默认 `false`；
- `verified_auto_deliver`：是否验证通过后自动推送，默认 `false`；
- `round_number`：当前轮次，从 1 开始；
- `round_phase`：`discovering`、`enriching`、`verifying`、`delivering` 或 `cooldown`；
- `round_started_at`：当前轮次开始时间；
- `next_round_at`：冷却结束时间；
- `round_metrics`：本轮候选、新增、验证匹配、验证拒绝、ERP 成功和失败数量；
- `round_checkpoint`：本轮已完成的关键词、候选、补全、验证与推送位置。

持续任务完成一轮后仍保持活动状态并占用一个调度名额，`round_phase` 变为 `cooldown`。冷却期间不发起模型或 ERP 请求，但会定期检查暂停与终止标记。

后端重启后按持久化状态恢复：

- 处于普通执行阶段的任务从最近安全检查点继续；
- 处于冷却阶段且尚未到时间的任务继续等待原 `next_round_at`；
- 冷却时间已经到达的任务直接进入下一轮；
- 恢复前重新读取成功 GUID 和指纹，防止重复推送。

每次进入新一轮只重置本轮检查点和本轮统计，不清除历史线索、验证记录、推送记录或全局去重基线。

## 暂停、继续与终止

- 暂停请求在当前单次模型、验证或 ERP 请求安全结束后生效，不再发起新的外部请求。
- 冷却期间点击暂停应立即进入 `paused`，并保留剩余冷却时间或原 `next_round_at`。
- 继续后重新进入调度队列；获得执行名额时从原阶段继续，不重做已完成步骤。
- 终止后保留全部结果、日志、下载和 ERP 状态，任务不可继续。
- 新建任务不会替换旧任务。系统继续使用现有最多两个并发任务和 FIFO 排队规则。

## 安全推送规则

现有 `auto_deliver` 是“联系方式补全后推送”，不能作为公司正式任务的安全通道。新流程使用独立的 `verified_auto_deliver`：

- 新建持续任务时，若开启 `verified_auto_deliver`，必须强制 `auto_deliver=false`；
- 两个自动推送模式不得同时开启；
- `verified_auto_deliver` 只在验证完成后运行资格判断；
- 旧任务的 `auto_deliver` 保持兼容，但页面将其与“验证后推送”明确区分；
- ERP 未配置时禁止开启验证后自动推送，但仍允许只采集、展示和验证。

资格判断集中在后端单一函数中，并在首次发送和失败重试前重复执行，避免 API、恢复流程或重试流程绕过规则。

## 前端展示

任务列表和详情增加以下信息：

- 当前轮次和当前阶段；
- 本轮候选数和新增公司数；
- 验证匹配数和拒绝数；
- ERP 推送成功数和失败数；
- 冷却阶段的下一轮开始时间；
- 持续采集与验证后自动推送是否开启。

采集结果继续逐条展示，不等待整轮结束。每条结果显示现有验证状态和 ERP 状态，包括仅展示、待验证、验证不通过、待推送、推送中、推送成功和推送失败。缺手机号、缺来源或验证未通过时，页面显示不能推送的原因，但不显示为任务异常。

## 接口变化

创建自然语言任务接口增加可选字段：

- `continuous_mode: bool = false`
- `verified_auto_deliver: bool = false`

任务详情与任务列表响应增加轮次、阶段、下一轮时间和本轮统计。现有暂停、继续和终止接口保持不变，并支持冷却阶段。

不新增用于绕过验证的 ERP 推送接口。现有手动推送能力继续保留，但公司正式任务的自动通道必须遵守本设计的安全门槛。

## 错误处理

- 模型限流、网络超时和临时失败沿用现有重试策略；重试耗尽后记录到当前步骤并继续能够继续的公司。
- 单个候选补全或验证失败不终止整轮。
- 整轮出现部分错误时仍保存统计并进入冷却，下一轮继续运行。
- ERP 失败不改变验证结果，也不把失败记录标记为成功。
- 来源链接必须是公开证据地址；模型名称、空字符串或无法解析的文本不得冒充来源。
- 任何资格字段缺失时默认不推送，不采用“可能正确”作为自动推送依据。

## 测试与验收

后端自动化测试覆盖：

- 新开关默认关闭，旧任务迁移后保持关闭；
- 每轮候选上限 100，轮次结束后进入 10 分钟冷却；
- 冷却结束自动进入下一轮，零新增轮次也不结束任务；
- 跨轮次公司和联系方式去重；
- 只有“手机号 + 来源链接 + 验证匹配”同时满足时才调用 ERP；
- 拒绝、分歧、失败、缺手机号和缺来源均不调用 ERP；
- ERP GUID 成功后在继续、重启和下一轮中不重复发送；
- 单条 ERP 失败不阻塞后续线索；
- 执行阶段和冷却阶段均可暂停、继续和终止；
- 后端重启能恢复当前轮次、冷却时间和检查点；
- 两个并发任务及 FIFO 排队行为不回归；
- 账号隔离、下载、手动 API 推送和普通一次性任务不回归。

前端验收覆盖：

- 两个开关位置明确且默认关闭；
- 任务列表能够展示持续任务、当前轮次、阶段和下一轮时间；
- 结果逐条出现，并正确展示验证与 ERP 状态；
- 暂停、继续、终止在采集阶段和冷却阶段都能正确操作；
- 页面刷新后轮次、统计和状态与后端一致。

深圳正式任务的最终验收标准是：任务可以持续多轮运行；只将满足安全门槛且未重复的线索逐条发送到 ERP；不符合条件的数据留在本地供人工查看；除人工暂停或终止外，任务不会自行结束。
