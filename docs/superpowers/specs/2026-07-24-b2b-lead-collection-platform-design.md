# B 端客户线索采集与核验平台设计

## 1. 文档状态

- 日期：2026-07-24
- 状态：已完成需求确认，待书面审阅
- 技术栈：React、TypeScript、Python、FastAPI
- 首批试点城市：武汉、长沙、成都、合肥、西安
- 部署目标：公司内网服务器；开发阶段允许本机运行

## 2. 背景与目标

家具企业需要通过自然语言描述目标客群，例如全案软装公司、设计公司、整装公司。系统接收任务后，应自动按城市、关键词、模型和数据源展开工作，持续执行到所有计划工作单元进入明确终态。

系统的核心目标如下：

1. 将自然语言需求转换为可审计、可重复执行的采集计划。
2. 自动完成五个试点城市的关键词搜索、候选企业发现、信息抽取、联系方式核验和去重。
3. 只将有可追溯公开证据的数据标记为“已核验”。模型输出本身不能作为真实性证据。
4. 按城市生成正式文件，并支持向外部系统 API 推送。
5. 支持多个系统用户和多个渠道账号，并保证任务、数据、文件、凭据和日志隔离。
6. 完整记录哪个账号在什么时间执行了什么任务和操作。

## 3. 范围边界

### 3.1 首版范围

- 使用武汉、长沙、成都、合肥、西安完成端到端验证。
- 默认客群关键词包括：软装公司、全案软装公司、全案设计公司、整装公司、整案公司。
- 用户可在任务启动前增删关键词；实际执行使用保存后的版本化关键词集合。
- 支持豆包和 DeepSeek，允许单选或全选。
- 支持模型 API、企业或搜索数据 API，以及经授权的网页账号适配器。
- 支持手机、邮箱、微信三类联系方式；至少有一类有效联系方式才可成为正式线索。
- 排除座机。
- 支持已核验与待人工复核两级结果。
- 支持 XLSX、CSV、按城市 ZIP 和外部 API 推送。

### 3.2 “全部完成”的可验收定义

互联网公开信息无法证明绝对覆盖某城市的全部公司。系统承诺的是确定性执行完整性，而不是无法验证的互联网绝对完整性。

一个任务的范围由以下矩阵确定：

`城市 × 关键词 × 已选模型 × 已选数据源 × 配置的分页或结果上限`

只有矩阵中的全部工作单元都进入“成功、无结果、明确失败、人工取消”之一，主任务才可结束。存在明确失败时，主任务状态必须为“完成但有异常”，并生成异常清单，不得静默标记成功。

### 3.3 首版不包含

- 不绕过验证码、账号风控或数据源访问控制。
- 不把手机号推断为微信号；只有来源明确标注微信时才保存为微信。
- 不将模型生成但无法找到来源证据的联系人写入正式结果。
- 不承诺每座城市固定线索数量。
- 不在首版建设 SaaS 计费、多租户商业套餐或公网开放注册。

## 4. 设计原则

1. **确定性编排**：工作流引擎决定任务是否完成，模型不能自行宣布搜索结束。
2. **证据优先**：每个正式联系人必须关联来源 URL、采集时间和证据记录。
3. **模型与事实分离**：模型负责理解、分类和抽取；公开来源负责事实证明。
4. **失败可见**：异常、重试、人工处理和取消都有显式状态和原因。
5. **隔离默认开启**：所有业务查询、文件路径和渠道凭据都带工作空间边界。
6. **适配器优先**：模型、数据源、浏览器和外部推送均通过稳定接口接入。

## 5. 总体架构

系统采用“API 控制中心 + 异步执行器 + 适配器 + 证据仓”的结构。

### 5.1 前端

- React + TypeScript 构建内网管理后台。
- 任务、城市进度、工作单元和推送状态通过 API 查询；实时状态采用服务端事件或轮询更新。
- 大数据表格使用服务端分页、排序和筛选。
- 前端不接收渠道明文密钥。

### 5.2 API 控制中心

- FastAPI 提供认证、任务管理、线索审核、导出、渠道配置和审计 API。
- SQLAlchemy 管理持久化模型，Alembic 管理数据库迁移。
- Pydantic 定义内部消息和外部接口契约。
- OpenAPI 文档作为前后端和外部系统联调依据。

### 5.3 异步执行层

- Redis 保存任务队列、锁、限流状态和短期进度缓存。
- 独立异步工作进程处理长任务，不占用 Web 请求进程。
- 工作单元具备幂等键，重复投递不会重复写入线索或重复推送。
- 临时错误按指数退避策略重试，默认最多三次，可按渠道配置。

### 5.4 数据与文件

- PostgreSQL 保存用户、工作空间、任务、企业、联系人、证据、核验、导出和审计记录。
- 原始证据快照和导出文件通过对象存储接口保存；试点可使用内网文件存储，部署时可替换为 S3 兼容存储。
- 数据库只保存对象路径、内容哈希和元数据，不把大文件直接写入业务表。

### 5.5 渠道适配器

- 模型适配器：豆包、DeepSeek。
- 数据源适配器：企业数据 API、地图或商户 API、搜索 API、企业官网发现器。
- 浏览器适配器：仅用于已授权网页账号和允许自动化访问的页面。
- 外部推送适配器：对接目标系统的 REST API 或 Webhook。

每种适配器统一返回结构化结果、原始响应引用、耗时、配额信息和错误类型。新增渠道不改变任务、核验和导出核心逻辑。

## 6. 用户、工作空间与权限

### 6.1 隔离模型

- 每个用户属于一个或多个工作空间。
- 任务、工作单元、企业、联系人、证据、导出、凭据和审计记录都包含 `workspace_id`。
- 后端从认证上下文获取工作空间，不接受前端任意指定越权工作空间。
- 文件保存路径包含不可猜测的工作空间和导出标识，下载必须再次鉴权。

### 6.2 角色

- 管理员：用户、角色、渠道配置、任务和审计管理。
- 运营人员：创建、启动、暂停、恢复和导出任务。
- 审核人员：查看证据并批准或拒绝待复核线索。
- 只读人员：查看任务和已授权结果，不可修改或导出敏感数据。

### 6.3 渠道凭据

- API 密钥和网页会话按工作空间保存。
- 凭据使用服务端主密钥加密，主密钥不存入数据库。
- 管理界面只显示掩码和最后验证时间，不提供明文回显。
- 日志、错误详情、导出和 API 响应必须自动脱敏。
- 网页账号登录过期或出现验证码时，暂停对应渠道并请求人工处理；不影响其他渠道和城市继续执行。

## 7. 任务生命周期

### 7.1 主任务状态

- `draft`：草稿。
- `planned`：执行矩阵已生成并冻结版本。
- `queued`：已进入队列。
- `running`：至少一个工作单元正在执行。
- `paused`：用户暂停，已完成结果保留。
- `needs_attention`：存在需要登录或人工处理的渠道。
- `completed`：所有工作单元正常结束且无失败。
- `completed_with_errors`：所有工作单元均已终止，但存在明确失败。
- `cancelled`：用户取消。
- `failed`：系统级错误导致任务无法继续规划或调度。

### 7.2 工作单元状态

- `queued`
- `running`
- `retry_wait`
- `succeeded`
- `no_result`
- `needs_attention`
- `failed`
- `cancelled`

暂停不会删除队列计划或已完成结果。恢复时只重新调度未进入终态的工作单元。每次状态变更都写入事件记录和审计日志。

### 7.3 执行流程

1. 用户输入自然语言目标、选择五个城市、关键词、模型和来源。
2. 规划器生成版本化执行矩阵，前端展示规模和预计调用量。
3. 用户点击启动，调度器为每个矩阵项创建幂等工作单元。
4. 模型和数据源适配器并行发现候选企业及公开来源。
5. 抽取器形成企业、地址、服务介绍和联系人候选。
6. 规范化器处理公司名、手机、邮箱和微信。
7. 核验器检查联系人是否在合格来源中精确出现。
8. 去重器在工作空间内合并联系人和企业。
9. 已核验线索进入正式线索库；证据不足的进入待复核库。
10. 城市工作单元完成后生成城市级统计；整个矩阵终止后生成任务总结。
11. 用户下载城市文件，或触发外部系统推送。

## 8. 多模型行为

### 8.1 模型职责

- 将自然语言目标解析为结构化客群条件。
- 对候选企业的业务类型和服务定位进行分类。
- 从已获取页面或 API 响应中抽取结构化字段。
- 为服务介绍生成忠于来源的摘要，并保留对应证据引用。

### 8.2 “全选”语义

选择豆包和 DeepSeek 时，两种模型可并行执行发现、分类或抽取工作。系统对结果做统一规范化和合并，而不是直接拼接两份答案。

模型共识不能替代来源核验。两个模型给出相同联系人，但没有公开来源证据时，该联系人仍不得成为已核验数据。

### 8.3 模型可追溯性

每次模型调用记录以下信息：

- 工作空间、任务和工作单元标识。
- 模型供应商、模型标识和提示词模板版本。
- 输入来源引用，不记录已配置为敏感的原始凭据。
- 响应引用、调用时间、耗时、状态和错误分类。
- 用量信息；供应商支持时记录 token 或计费单元。

## 9. 数据核验规则

### 9.1 联系方式规范化

- 中国大陆手机号去除空格、连字符和 `+86` 前缀后，必须符合 `1[3-9][0-9]{9}`。
- 包含区号、短号或固定电话格式的号码标记为座机或未知号码，不进入正式联系人。
- 邮箱去除首尾空格并统一域名大小写，必须通过语法校验。
- 微信号只在来源明确标注“微信、微信号、WeChat”时保存；不得因手机号可用于微信而推断。
- 无法可靠分类的联系方式进入待复核或拒绝状态。

### 9.2 来源等级

合格强来源包括：

- 企业官网的联系页面或明确属于该企业的页面。
- 经过认证的地图或商户页面。
- 企业官方公开主页或经过认证的公开企业账号页面。
- 合法企业数据服务提供的明确字段及来源说明。

弱来源包括未认证目录、聚合页面、模型摘要和缺少企业归属证明的页面。弱来源可以发现候选，但不能单独产生已核验联系人。

### 9.3 结果等级

- `verified`：至少一个非座机联系方式在合格来源中精确出现，来源页面在采集时可访问，并保存证据记录。
- `pending_review`：找到候选联系方式，但来源等级、企业归属或字段类型不足以自动确认。
- `rejected`：无来源、格式无效、属于座机、与企业不匹配或审核人员拒绝。

人工审核必须记录审核人、时间、结论和理由。人工批准不能删除原始证据或自动核验记录。

### 9.4 证据记录

每条证据至少保存：

- 来源 URL 和来源渠道。
- 页面标题或数据集记录标识。
- 采集时间和 HTTP 或渠道响应状态。
- 包含目标字段的最小必要文本片段或结构化响应引用。
- 原始内容对象路径和内容哈希。
- 采集适配器及版本。

## 10. 去重与合并

### 10.1 联系人唯一键

在同一工作空间内分别使用以下标准化值作为强唯一键：

- `mobile_normalized`
- `email_normalized`
- `wechat_normalized`

不同联系方式不会互相替代。一家公司可保存多个手机、邮箱和微信。

### 10.2 企业辅助键

使用“标准化公司名 + 城市”作为企业合并辅助键。标准化只处理空白、常见标点、全半角和明确的公司后缀差异，不进行可能误合并的模糊猜测。

企业名相似但强唯一联系人不同的记录进入待复核合并队列，不自动合并。

### 10.3 合并规则

- 相同强唯一联系人指向同一企业时，合并证据、来源和发现渠道。
- 相同强唯一联系人指向不同企业时，保留冲突并进入人工复核。
- 新证据不会覆盖旧证据；服务介绍和地址保存版本及来源。
- 导出时按企业聚合联系方式，并保持每种联系方式内部唯一。

## 11. 核心数据实体

- `users`：系统用户及状态。
- `workspaces`：隔离边界。
- `workspace_memberships`：用户、工作空间和角色。
- `provider_credentials`：加密渠道凭据及验证状态。
- `tasks`：自然语言需求、结构化条件、状态和版本。
- `task_cities`：城市级进度和统计。
- `task_work_units`：城市、关键词、模型和来源的执行单元。
- `provider_runs`：每次适配器调用及结果引用。
- `companies`：标准化企业信息。
- `company_profiles`：地址、服务介绍及其版本来源。
- `contacts`：手机、邮箱、微信及标准化值。
- `lead_evidence`：字段级来源证据。
- `lead_verifications`：自动和人工核验记录。
- `task_leads`：任务与企业结果的关联和状态。
- `exports`：文件生成、范围、状态和对象路径。
- `delivery_attempts`：外部系统推送尝试和幂等状态。
- `audit_logs`：用户和系统操作审计。

所有业务实体使用不可猜测标识、创建时间、更新时间和工作空间标识。关键状态变更使用乐观锁或数据库锁，防止重复执行导致覆盖。

## 12. 前端信息架构

### 12.1 主要页面

1. **任务中心**：新建任务、查看总体和城市进度、暂停、恢复、取消和异常处理。
2. **任务详情**：执行矩阵、工作单元、模型调用、来源结果、城市统计和活动时间线。
3. **线索库**：按城市、客群、联系方式类型、渠道和核验状态筛选。
4. **待复核**：并排显示企业字段、联系人、证据片段和来源链接，支持批准或拒绝。
5. **导出与 API**：生成城市文件、下载 ZIP、配置字段映射、查看推送记录和重试失败项。
6. **渠道账号**：配置豆包、DeepSeek及其他数据源，显示掩码、连通性和配额状态。
7. **用户与审计**：管理成员角色，查询任务、审核、导出和配置变更日志。

### 12.2 关键交互

- 新建任务使用分步表单，但启动后所有城市和关键词自动运行，不需要逐城市点击。
- 启动前展示计划工作单元总数，避免用户误触发超出预期的调用。
- 城市表格显示状态、工作单元进度、已核验数、待复核数、异常数和最近活动。
- 登录过期或验证码显示明确的“需要处理”状态，并提供恢复后继续入口。
- 正式导出默认只包含已核验数据；待复核数据必须通过独立、明确标记的导出操作获取。

## 13. API 设计

API 统一使用 `/api/v1` 前缀和 JSON。列表接口使用服务端分页。所有写操作返回可追踪请求标识。

### 13.1 主要内部接口

- `POST /tasks`：创建任务草稿。
- `POST /tasks/{task_id}/plan`：生成并冻结执行矩阵。
- `POST /tasks/{task_id}/start`：启动任务。
- `POST /tasks/{task_id}/pause`：暂停任务。
- `POST /tasks/{task_id}/resume`：从断点恢复。
- `POST /tasks/{task_id}/cancel`：取消未完成工作单元。
- `GET /tasks/{task_id}`：任务摘要。
- `GET /tasks/{task_id}/work-units`：工作单元和错误详情。
- `GET /leads`：筛选线索。
- `GET /leads/{lead_id}`：查看企业、联系人和证据。
- `POST /leads/{lead_id}/reviews`：提交人工审核结论。
- `POST /exports`：创建城市或任务导出。
- `GET /exports/{export_id}`：查询生成状态。
- `GET /exports/{export_id}/download`：鉴权下载。
- `POST /deliveries`：创建外部系统推送。
- `POST /deliveries/{delivery_id}/retry`：重试失败项。
- `GET /audit-logs`：按权限查询审计日志。

### 13.2 外部推送

外部推送适配器支持：

- 服务地址和鉴权方式配置。
- 城市、公司、联系人和证据字段映射。
- 批量大小、超时和重试策略。
- 幂等键，默认由工作空间、线索标识和数据版本组成。
- 单条或批次响应记录。
- 部分失败拆分重试，成功项不重复发送。

目标系统接口合同尚未提供时，首版实现通用 REST 适配器和本地模拟接收端。真实推送验收在接口合同和测试凭据提供后执行，不影响文件下载闭环。

## 14. 导出设计

### 14.1 文件组织

- 每座城市生成独立 XLSX 和 CSV。
- 多城市下载生成 ZIP。
- 文件名包含城市、任务简称和生成时间。
- 正式文件只包含 `verified` 数据。
- 待复核数据如需下载，生成独立文件并在文件名和工作表中明确标注。

### 14.2 正式结果字段

- 城市
- 公司名称
- 手机号码
- 邮箱号码
- 微信号码
- 公司地址
- 服务定位介绍
- 核验状态
- 发现渠道，例如豆包、DeepSeek或企业数据源
- 核验来源渠道
- 来源 URL
- 采集时间
- 核验时间
- 保存日期
- 任务标识

“发现渠道”和“核验来源渠道”必须分开。豆包发现的线索如由企业官网完成核验，不能把豆包写成真实性证据来源。

## 15. 日志与可观测性

### 15.1 审计日志

至少记录：

- 操作用户、工作空间和角色。
- 操作时间、请求标识和来源地址。
- 操作类型及目标对象。
- 创建、启动、暂停、恢复、取消、审核、导出、推送、凭据修改和权限修改。
- 不含密钥和完整认证信息的变更摘要。

审计日志默认保存 180 天，管理员可按公司制度调整。导出和删除敏感数据同样需要审计。

### 15.2 运行指标

- 按任务、城市、关键词、模型和数据源统计工作单元数。
- 成功、无结果、重试、需要处理和失败数量。
- 调用耗时、错误率、限流次数和配额使用量。
- 候选数、已核验数、待复核数、拒绝数和去重合并数。
- 文件生成和 API 推送成功率。

## 16. 错误处理

- 网络超时、临时服务错误和限流进入可重试错误。
- 无效凭据、登录过期和验证码进入 `needs_attention`，不自动反复尝试。
- 响应格式变化进入适配器解析错误，保存脱敏样本引用供排查。
- 数据格式无效进入记录级拒绝，不使整个城市任务失败。
- 数据库或对象存储不可用时暂停相关工作单元，避免确认消息后丢失结果。
- API 推送失败与采集任务状态分离；采集完成的数据仍可下载和稍后重推。
- 所有最终失败必须包含稳定错误码、可读原因、首次和最后发生时间及重试次数。

## 17. 测试策略

### 17.1 单元测试

- 城市和关键词矩阵生成。
- 手机、邮箱、微信和座机识别。
- 公司名规范化。
- 联系方式强唯一键去重。
- 企业合并和冲突规则。
- 核验状态判定。
- 主任务完成状态聚合。
- 导出字段和敏感信息脱敏。

### 17.2 适配器合同测试

每个模型、数据源、浏览器和推送适配器必须通过同一合同测试，包括正常结果、无结果、限流、超时、登录失效、格式变化和部分失败。

在真实凭据到位前，模拟适配器只用于流程测试。模拟产生的数据必须带测试标识，且系统禁止其进入正式导出和真实 API 推送。

### 17.3 集成测试

- FastAPI、PostgreSQL、Redis、工作进程和对象存储的完整任务链路。
- 并发工作单元的幂等执行。
- 暂停、恢复、重试和取消。
- 核验、人工审核、去重、导出和推送。
- 两个工作空间之间的数据、文件、凭据和审计隔离。

### 17.4 端到端验收

使用五个试点城市执行完整任务，并验证：

1. 一次启动自动展开全部配置工作单元。
2. 所有工作单元最终进入可解释状态。
3. 正式线索至少包含一个有效的手机、邮箱或微信，且不含座机。
4. 正式线索的每个联系方式都能追溯到合格来源证据。
5. 重复联系方式不会在同一工作空间内形成重复正式线索。
6. 每座城市可独立生成 XLSX 和 CSV，多城市可生成 ZIP。
7. 推送具备幂等性，重试不会重复创建成功记录。
8. 登录过期只暂停对应渠道，其他城市和渠道继续执行。
9. 不同工作空间无法读取或下载彼此数据。
10. 关键操作都能在审计日志中查到账号、时间、任务和结果。

验收不以每座城市达到固定数量为条件。数量取决于配置范围、来源覆盖和公开数据可得性。

## 18. 部署与运维

- 内网服务器部署 Web、API、工作进程、PostgreSQL、Redis和对象存储组件。
- 反向代理统一提供 HTTPS、请求大小限制和访问日志。
- Web 与 API 使用同源访问，认证 Cookie 设置为 `HttpOnly`、`Secure` 和适当的 `SameSite` 策略。
- 数据库和对象文件按公司制度备份，并定期验证恢复。
- 渠道并发和速率按供应商限制配置，不以更换运行时版本规避访问或镜像问题。
- 开发、测试和生产使用独立数据库、凭据和存储路径。

## 19. 实施前置条件

设计和模拟闭环不依赖真实密钥。真实渠道验收需要后续提供：

- 豆包网页账号或火山方舟 API 凭据及允许使用的模型信息。
- DeepSeek 网页账号或 API 凭据及允许使用的模型信息。
- 企业、地图或搜索数据源的账号、配额和使用条款。
- 目标系统的接口文档、测试地址、鉴权方式、字段要求和幂等规则。

凭据通过受控配置流程录入，不通过代码、聊天记录、Git 或普通文档传递。

## 20. 设计结论

首版采用“API 核心 + 可插拔浏览器采集”的混合架构。React 管理后台提供任务、核验和交付操作；FastAPI 和异步执行层保证五城执行矩阵完整运行；豆包和 DeepSeek用于理解、分类和抽取；企业 API、地图、官网及其他公开来源提供事实证据；核验、去重、工作空间隔离和审计作为不可绕过的核心流程。

该设计优先完成一个稳定、可追溯、可验收的五城闭环，并保留扩展到全国三线及以上城市和更多模型、数据源、外部系统的能力。
