# 豆包最终联系方式补采设计

## 目标

候选公司可由用户选择的豆包、DeepSeek 或多个模型发现，但每家公司的联系方式、地址和服务简介最终必须由豆包单独查询。DeepSeek 不再作为联系方式补采的回退模型。

## 数据流程

1. 根据用户自然语言解析城市、客户类型、数量和所需联系方式。
2. 使用用户勾选的模型生成公司候选名单，并保留候选发现渠道。
3. 按城市和公司名称去重。
4. 对每个候选公司固定调用豆包 `enrich_company`，一次请求只查询一家公司。
5. 保存豆包返回的手机号、邮箱、微信、地址、服务简介和来源链接。
6. 未查到的字段保存为空，并在页面显示“未公开”，不得编造。

## 模型与失败规则

- 前端模型选择只控制候选公司发现。
- 最终联系方式补采模型固定为豆包。
- 豆包请求发生临时错误时重试两次。
- 重试后仍失败则将该公司标记为“豆包补采失败”，保留候选记录，不回退 DeepSeek。
- 豆包请求成功但没有公开联系方式时标记为“豆包已查询”，联系方式显示“未公开”。

## 历史任务处理

现有候选记录可重新进入豆包补采流程。重新补采不重新生成公司名单，并用豆包结果覆盖此前 DeepSeek 的补采字段；候选发现渠道保持不变。

## 展示字段

- `discovery_channel`：候选公司由哪个模型或公开网页发现。
- `enrichment_model`：联系方式补采模型，成功时固定为 `doubao`。
- `enrichment_state`：`pending`、`completed` 或 `failed`。
- 联系方式为空时显示“未公开”。

## 验证

- 自动化测试确认只调用豆包补采，即使任务同时选择 DeepSeek。
- 自动化测试确认豆包失败时不会调用 DeepSeek 补采。
- 自动化测试确认历史候选可以重置后重新由豆包补采。
- 使用真实豆包兼容接口完成一家公司补采测试，不在日志中输出 API 密钥。
